# 0001. 設計の決定を ADR に記録する

- 状態: 採用
- 日付: 2026-11-12

## 背景

設計の判断とその理由は、issue のコメントに残していた。0.13 の仕様を決める過程で、次の問題が出た。

- 決定がコメントの積み重ねの中にあり、issue のタイトルや本文と食い違う。結論を知るには、コメントを最後まで読む必要がある
- 決定を一覧できる場所が無い
- 個別の決定の前提になる考え方（宣言とインタープリターの関係など）を書く場所が無い

議論の過程は残す必要がある。issue はリリースからも参照される。

## 決定

役割を分ける。

| 場所 | 役割 | 書き換えかた |
|---|---|---|
| issue のコメント | 議論の過程 | 追記するだけ |
| issue の本文の冒頭 | その issue の現在の決定の要約と、ADR へのリンク | 決定が変わったら書き換える |
| `docs/adr/` | 決定 1 つにつき 1 ファイル | 書き換えない。覆すときは新しい ADR で置き換える |
| `docs/design.md` | 決定を導く考え方 | 更新していく |

## 採らなかった案

- **issue のコメントだけに残す（これまでの運用）。** 上の問題がある
- **RFC の手続き（提案の文書を PR で審査する）。** この規模のプロジェクトには重い

## 帰結

- 決定が出たら、ADR を書き、issue の本文の冒頭を更新する
- 実装の PR は ADR を参照できる
