# wp-resta の設計の考え方

wp-resta を実装・変更するときの、判断の前提を書く。

- 利用者への約束は [spec.md](spec.md) にある
- 個別の決定とその理由は [adr/](adr/README.md) にある
- ここに書くのは、決定を導く考え方。規則の一覧ではない。具体的な経緯や実例は ADR と issue に置き、ここからは指し示すだけにする

## 誰の、どの問題を解くか

### 想定する利用者

それなりの規模の WordPress の REST API を開発・運用していて、フックの予測しづらさ、制御しづらさに困っている人。

### 問題

WordPress の汎用エンドポイントをフックで調整して運用していると、次のことが起きる。

- パラメータの組み合わせが開いているので、発行されるクエリを事前に予測できない
- 望ましくないクエリを抑えるためにフックを書くと、それが別の場所で副作用を生む

用途別のエンドポイントに分けると、これが変わる。

- パラメータの集合が閉じ、ユースケースが有限になる。発行されるクエリを予測できる
- 監視で、問題のあるエンドポイントを特定できる
- エンドポイントが互いに独立するので、対処を立てやすい。その場かぎりの対処をしても、影響が限られる

ただし、用途別のエンドポイントを自前で作るには、阻むものが 2 つある。

- **規約が無い。** `register_rest_route()` をどこに書くかは決まっていない。ルートの定義がどこにあるかは、探さないとわからない
- **仕様がサーバーにしか無い。** 汎用エンドポイントの仕様は公開されていて、広く知られている。自前のエンドポイントは、何を受け取り何を返すかが、サーバーのコードにしか書かれていない

### wp-resta が与えるもの

- **規約。** Route クラス 1 つがエンドポイント 1 つで、決まったディレクトリに置く
- **契約。** Route クラスの宣言から OpenAPI を導出する。フロントエンドのコードは、この仕様に依存すればよい

### 残るもの

エンドポイントが用途別になり、フロントエンドとの契約が OpenAPI として書かれていれば、目的は達している。契約が残れば、wp-resta 自体は差し替えてもよい。

## カーネルを小さく、ユーザーランドを広く

- **フレームワークが負う責任を小さくし、利用する側の開発者が変更できる余地を、可能なかぎり大きく取る。**
- フレームワークが決めて約束するほど、利用する側の余地は狭くなり、フレームワークが保守するものは増える
- 機能は安く書けるようになった。保守の責任は安くならない。書けることは、入れる理由にならない

イメージは Linux である。カーネルがあり、その周りにユーザーランドがある。人が「Linux」と聞いて思い浮かべるもののほとんどは、ユーザーランドで作られている。Ubuntu はデスクトップでそのまま使える構成を用意し、サーバーなら Debian を選ぶかもしれない。用途ごとに適切なデフォルトは違うので、カーネルは 1 つの使いかたを強制しない。

wp-resta に当てると、次のようになる。

- **カーネル**: 宣言を読み、解釈して、実行する最小の仕組み
- **デフォルトの構成**: `AbstractRoute` の書きかた（定数、`callback()`、`body` プロパティ）、組み込みのフック、認可のアトリビュートなど。同梱しているが、カーネルではない。ある用途向けに組んだ 1 つの構成であり、唯一の正解ではない

何かを足すときは、「これはカーネルに要るのか、デフォルトの構成の側で足りるのか」を問う。

以下の節は、どれもこの考えの別の面である。

## 宣言とインタープリター

- **Route クラスは宣言である。** 定数、メソッドのシグニチャ、アトリビュート、プロパティで、開発者が意図を表明する
- **wp-resta は、その宣言のインタープリターである。** 宣言を読み、解釈して、登録・検証・実行・OpenAPI の生成を行う
- 「定義と実行を分ける」とは、この関係のこと。Route クラスは実行の担当者ではない

判断の目安は、フレームワークがルートを「呼ぶ」のか「読む」のか。

- 決まったメソッドをルートに実装させて、フレームワークが呼ぶ。これは実行モデルを定義に強制している
- ルートに書かれたものをフレームワークが読んで、解釈する。これは意図の表明を解釈している

後者を選ぶ。ここから次のことが導かれる。

- `RouteInterface` にメソッドを増やさない。任意の機能を interface で強制しない
- 宣言は、ルートのインスタンスが無くても読める形にする（クラスの Reflection で足りる）
- 実行時の値は callback の引数で受ける。ルートのプロパティに書き込まない

## 検査は、表明されたものだけを行う

- **フレームワークは、検証や認可を自分の判断で執行しない。** 開発者が宣言で表明した検査だけを行う
- 表明が無ければ、何もしない。それも意図の表明として扱う。`callback(int $id)` は整数の検証を求めていて、`callback($id)` は求めていない
- フレームワークが用意するのは、表明するための語彙（型、アトリビュート）と、その解釈である
- 宣言で書けない判断（実行時の値に依存するもの）は、開発者がコードで書く。宣言の語彙に無理に持ち込まない

## 仕様とデフォルトを区別する

- **仕様**は約束である。spec.md に書いたものは、担保し、保守する責任を負う。変えれば破壊的変更になる
- **デフォルト**は、そう振る舞うというだけのこと。利用者に優しいほうを選んでいるにすぎず、約束ではない

細かいこと、どちらでもよいことを、仕様と呼ばない。約束を増やすと、フレームワークが保守するものが増え、利用する側が決められる余地が減る。それを明示的な仕様にしたい場合は、利用する側の開発者が自分のコードでそう決めればよい。

何かを決める必要があることと、それを仕様にする必要があることは違う。「決めたほうがよい問題」の多くは、デフォルトをどうするかの問題である。

細かいことを仕様と呼ぶと、それを保守するための構造が要るようになり、構造が interface に現れる。何かを spec.md に書く前に、次を問う。

- これは約束か、それともデフォルトか
- 約束にした場合、それを保守するために何が固定されるか
- 解こうとしている問題の大きさに、増える約束は釣り合っているか

実例: [ADR 0003](adr/0003-remove-validate-authorize.md) の「背景」（検証と認可の順序）。

## クラスのあいだでも、依存される面を小さくする

仕様を増やさないのと同じことを、フレームワークの内側でも行う。public メソッドは、クラスが呼ぶ側に対してする約束である。依存されれば、変えにくくなる。

利用する側と利用される側のあいだのインターフェースを、最小にする（情報隠蔽）。これは規則ではなく、判断の基準である。クラス間の呼び出しや public メソッドを足すとき、次を問う。

- この変更で、呼ぶ側が新しく知らなければならないことは何か
- それは、呼ぶ側の役割に必要な知識か

この基準から見たとき、次のようになる。

- **public メソッド**は「依存してよい」というメッセージになる。呼ぶ側の都合で開けたのか、必然性があって開いているのかは、後からは区別できない。数の問題ではなく、public を通じて内部の構造が呼ぶ側に漏れることが問題である
- **interface** は、処理の流れを記述し、依存を明示するためにある。処理の根本的な流れは interface で規定する。流れに関わらないものまで interface にしない
- **DI で組み立てるもの**は、差し替えられる状態にしておく。interface が宣言されていなくても、置き換えられる余地を残す
- **`final`** は、拡張を意図的に閉じるときに使う。問うのは、差し替えを前提に組んだ関係を塞いでいないか、である

実例: [#113](https://github.com/amashigeseiji/wp-resta/issues/113)（`RequestHandler` が `Operation` と `Callback` について知っていること）。

## インターフェースを変えるとき

- **変更は方向性から導く。** いま合意している方向性は 2 つ。ルート（定義）と実行を分けること、callback の引数と戻り値の型をそのままスキーマにすること。どちらから導かれるかを言えない変更は、しない
- **解決済みの小さい問題で、インターフェースを大きく変えない。** 実例: [ADR 0005](adr/0005-static-route-body.md) の「背景」
- **一般論の良し悪しだけを根拠にしない。** 状態、`final`、書き方が 2 つある、といった指摘は、それだけでは変更の理由にならない
- **「何もしない」を既定にもしない。** 問題は、増やすものと減らすもののバランスである
- **迷っているあいだは、決めない。** 決めなくてよいことは多い。迷いが残ること自体が、その論点が重要であることを示している。非推奨の宣言や削除の予告は利用者への約束なので、迷いが残るうちは出さない。実例: [ADR 0005](adr/0005-static-route-body.md) の「背景」
